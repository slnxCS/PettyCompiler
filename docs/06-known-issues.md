# 06 — Ограничения и известные проблемы

Список составлен по результатам чтения кода и компиляции тестовых программ. Для каждой проблемы указаны
место в коде и минимальный воспроизводящий пример.

## 1. Ошибки, приводящие к неверному байткоду

Эти проблемы опаснее остальных: компиляция проходит успешно, но результат некорректен.

### 1.1. Вложенные `if` получают неверный адрес перехода

`Compiler.CompileIf` (`Compiler/Compiler.cs`) вычисляет адрес перехода после генерации тела и вставляет его
через `compiled.InsertRange`. Вставка 4 байт внешним `if` сдвигает код вложенного `if`, чей абсолютный адрес
уже вычислен, — внутренний переход промахивается на 4 байта и попадает в середину инструкции.

```petty
func Main() : {
    if true : {
        if true : { print(1); }
        print(2);
    }
}
```

Внутренний `JMP_IF_FALSE` указывает на `0x41` (середина `SYS_CALL`), а должен — на `0x45`.
**Исправление:** писать заглушку `Emit(0)` и затем перезаписывать её на месте (пример — в
[05-extending.md](05-extending.md#3-новая-инструкция-языка)).

### 1.2. Вещественные литералы зависят от системной локали

`Lexer._addNumber` заменяет `.` на `,`, а `Parser.parsePrimaryBasicExpression` вызывает `float.Parse` с
текущей культурой. В локали `ru-RU` это работает, в `en-US`/invariant запятая считается разделителем
тысяч: литерал `2.5` компилируется как `25.0` (проверено с `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`).
**Исправление:** оставлять `.` и парсить с `CultureInfo.InvariantCulture`.

### 1.3. `int32 / int32`: тип `float32`, инструкция `DIV_INT`

`Int32InstanceSymbol.VisitBinary` возвращает для `/` тип `float32`, а `operators["/"]` — `OpCode.DIV_INT`.
Последующий код (например, выбор перегрузки `print(float32)` → `SYS_CALL 1`) рассчитывает на `float32` на
стеке. Корректно, только если VM в `DIV_INT` кладёт `float32`. Нужно согласовать: либо тип результата
`int32`, либо отдельная инструкция.

### 1.4. Класс `Array` отсутствует в таблице классов

`Analyzer.InitClassList` не добавляет `BuiltIn.ArrayClass`, поэтому в таблице классов есть ID 0, 1, 2, 4, 5,
6, 7, 8… без 3. Если VM индексирует классы по позиции в таблице, все классы начиная с `int32` сместятся.
**Исправление:** `AddClassToList(BuiltIn.ArrayClass)`.

### 1.5. `SortFunctionsByID` ничего не сортирует

Оба метода `Compiler.SortFunctionsByID` присваивают отсортированный список **параметру метода**, поэтому
сортировка теряется, и функции выводятся в порядке добавления в `analyzer.Functions`. Функция добавляется
туда *после* анализа своего тела, а ID получает *до*, поэтому при функции, объявленной внутри другой
функции, порядок в секции разойдётся с ID. Для обычных программ порядок совпадает случайно.
**Исправление:** сортировать список на месте (`list.Sort(...)`) или возвращать результат.

### 1.6. Значение вызова-инструкции остаётся на стеке

`f();` для функции с не-`void` результатом оставляет значение на стеке — инструкции `POP` нет. В циклах
(когда они появятся) это приведёт к росту стека.

### 1.7. Поля без инициализатора

Поля `var y : int32;` не инициализируются базовым конструктором — их значение определяется VM
(в коммите `1d43233` описано как «garbage values»).

## 2. Падения компилятора на допустимом синтаксисе

Конструкции, которые проходят парсер, но вызывают системное исключение вместо понятной ошибки.

| Пример | Исключение | Место |
|---|---|---|
| `var x : int32;` внутри функции | `NullReferenceException` | `CompileVarDef` компилирует `Value == null` |
| `var g : int32;` на верхнем уровне | `NullReferenceException` | `WriteGlobals` |
| `x += 1;` (и `-=`, `*=`, `/=`) | `NotImplementedException: +=` | `VisitVarAssigment` |
| `if 1 : { }` | `NotImplementedException` | `VisitIf` — нет сообщения об ошибке типа |
| `var g = f;` (функция как значение) | `Error: Value required` с позицией `(0;0)` | `GetInstanceSymbol` |
| `class A : { func A() : { } }` + `A()` | `Error: Function 'A' is already exist` с позицией `(0;0)` | `BasicConstructorSymbol` |

## 3. Не реализовано

| Возможность | Состояние |
|---|---|
| `else` | ключевое слово есть, парсер — нет |
| Циклы | отсутствуют (только рекурсия) |
| Операторы сравнения кроме `int32 == int32` | нет `!=`, `<`, `>`, `<=`, `>=`; нет `==` для `float32`/`bool` |
| Логические операторы | нет `and`/`or`/`not` |
| Унарный минус | только как часть числового литерала |
| Составное присваивание | разбирается, не анализируется |
| Строки | нет класса `String`; литерал даёт ошибку |
| Символьные литералы | `_addChar` не поглощает закрывающую `'` → `'a'` даёт `Char termination required`; парсер `Char` не обрабатывает |
| `import` / `package` | только ключевые слова |
| Наследование | ID родителя пишется в байткод, но члены не наследуются; подтипов нет |
| Пользовательские конструкторы | метод с именем класса конфликтует с базовым конструктором; аргументы конструктора не поддерживаются |
| Доступ к полям без `self.` | не поддерживается |
| Вложенные классы | молча игнорируются |
| Индексатор `a[i]` | поля `ArrayAppealArguments*` в AST есть, разбор — нет |
| Массивы других типов | `Array` хранит только `int32` (`get`/`set`) |
| Функции первого класса, замыкания | нет |
| Использование до объявления | функции и классы должны быть объявлены выше места использования (кроме методов внутри класса) |
| Проверка всех путей возврата | проверяется только наличие хотя бы одного `return` |

## 4. Качество кода и инфраструктура

- **Статическое состояние** (`BuiltIn`, `ConstantPool`, `Scope.GlobalFreeIDSet`, `Analyzer.MainFunction`)
  не сбрасывается: повторная компиляция в том же процессе даёт неверные ID, лишние константы и ошибку
  `Main entry point is already exist`.
- **Отладочный путь в `Program.cs`.** В Debug-сборке аргументы игнорируются и используется абсолютный путь
  `/home/slnx/...`, привязанный к машине разработчика.
- **Исключения не перехватываются** — пользователь видит стек вызовов вместо одного сообщения. Блок
  `try/catch` в `Program.cs` закомментирован.
- **Имя выходного файла** зашито (`compiled.pt`); нет опции `-o`.
- **Дублирование кода:**
  - `Lexer`: пары `_addX` / `_processX`; вторые не используются.
  - `Analyzer`: `ResolveFuncDecl` и `VisitFuncDeclWithoutBlock` почти идентичны;
    `VisitVarDef` и `ResolveFieldsDecl` — тоже.
  - Два `ContainsOverload` в `FunctionSymbol`.
- **Мёртвый код:** `Parser.parseIdentifier(Expression)`, `parseAfterIdentifierExpression`,
  `VarSymbol.GetStoreBytes`, `Symbol.GetOwner`, `IdentifierExpressionPart.SelfPushBytes`/`Last()`,
  `ScopeType.Package`, `using System.Runtime.Intrinsics.Arm` в `Parser.cs`.
- **Опечатки в идентификаторах и сообщениях:** `ComileFabric.cs`, `VarAssigment`, `returnFinded`,
  `Asteric`, `ArrayAppealArgumentsAftersFuncCall`, `"Excepted file name"`, `"does not exsist"`,
  `GlobalsLenght`.
- **Устаревший комментарий** с порядком секций в `CompileFabric.cs`.
- **`bin/` и `obj/` под контролем версий**, хотя указаны в `.gitignore` (файлы добавлены раньше правила).
  Рекомендуется `git rm -r --cached PettyLang/bin PettyLang/obj`.
- **Тесты** покрывают только лексер и парсер.

## 5. Рекомендуемый порядок исправлений

1. Адреса переходов во вложенных `if` (1.1) и культура парсинга чисел (1.2) — небольшие правки,
   устраняют неверный байткод.
2. `Array` в таблице классов (1.4), сортировка функций (1.5), согласование `DIV_INT` (1.3).
3. Перехват `Error` в `Program.cs` и замена `NotImplementedException`/`NullReferenceException` на
   понятные ошибки (раздел 2); инициализация переменных без значения значением по умолчанию.
4. Сброс статического состояния (или перевод его в экземпляр «контекста компиляции») — это нужно
   для тестов анализатора и генератора.
5. Языковые возможности: `else`, циклы, операторы сравнения, `POP` для отбрасываемых значений.
