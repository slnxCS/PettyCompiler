# 06 — Ограничения и известные проблемы

Список составлен по результатам чтения кода, компиляции тестовых программ и автотестов. Для большинства
ошибок есть тест в `Tests/PettyCompilerTests/KnownBugTests.cs` (категория `KnownBug`): он описывает
правильное поведение и начнёт проходить, когда ошибка будет исправлена.

## 1. Ошибки, приводящие к неверному байткоду

Эти проблемы опаснее остальных: компиляция проходит успешно, но результат некорректен.

### 1.1. Вложенные `if` получают неверный адрес перехода

`Compiler.CompileIf` (`Compiler/Compiler.cs`) вычисляет адрес перехода после генерации тела и вставляет его
через `compiled.InsertRange`. Вставка 4 байт внешним `if` сдвигает код вложенного `if`, чей абсолютный адрес
уже вычислен, — внутренний переход промахивается на 4 байта и попадает в середину инструкции.

```petty
func Main() {
    if true : {
        if true : print(1);
        print(2);
    }
}
```

**Исправление:** писать заглушку `Emit(0)` и затем перезаписывать её через `SetReservedBytes` — так уже
заполняется длина функции (пример — в [05-extending.md](05-extending.md#3-новая-инструкция-языка)).
Тест: `KnownBugTests.NestedIfJumpTargets`.

### 1.2. Приведение к тому же типу теряет значение — [#7](https://github.com/slnxCS/PettyCompiler/issues/7)

`var a = 1 as int32;` компилируется без `PUSH_CONSTANT`: `Symbol.CompileCastBytes` при `castType == Type`
сразу выходит, не скомпилировав `expression.Value`. В VM значение не попадает на стек.
Тест: `KnownBugTests.CastToSameTypeKeepsValue`.

### 1.3. Вещественные литералы зависят от системной локали

`Lexer._addNumber` заменяет `.` на `,`, а `Parser.parsePrimaryBasicExpression` вызывает `float.Parse` с
текущей культурой. В локали `ru-RU` это работает, в `en-US`/invariant запятая считается разделителем
тысяч: литерал `2.5` компилируется как `25.0`.
**Исправление:** оставлять `.` и парсить с `CultureInfo.InvariantCulture`.
Тест: `KnownBugTests.FloatLiteralDoesNotDependOnCulture`.

### 1.4. `SortFunctionsByID` ничего не сортирует

Оба метода `Compiler.SortFunctionsByID` присваивают отсортированный список **параметру метода**, поэтому
сортировка теряется, и функции выводятся в порядке добавления в `analyzer.Functions`. Функция добавляется
туда *после* анализа своего тела, а ID получает *до*, поэтому при функции, объявленной внутри другой
функции, порядок в секции разойдётся с ID. Для обычных программ порядок совпадает случайно.
**Исправление:** сортировать список на месте (`list.Sort(...)`) или возвращать результат.
Тест: `KnownBugTests.FunctionsSectionIsSortedById`.

### 1.5. Значение вызова-инструкции остаётся на стеке

`f();` для функции с не-`void` результатом оставляет значение на стеке — инструкции `POP` нет. В циклах
(когда они появятся) это приведёт к росту стека.

### 1.6. Поля и элементы массива без инициализатора

Поля `var y : int32;` не инициализируются базовым конструктором, а элементы массива — при `Array(n)`.
Их значение определяется VM (сейчас — неинициализированная память).

## 2. Неверные или неудобные сообщения об ошибках

### 2.1. Ошибки в теле не-`void`-функции подменяются — [#8](https://github.com/slnxCS/PettyCompiler/issues/8)

`Analyzer.VisitFuncBlock` проверяет наличие `return` в блоке `finally`. Если тело выбросило ошибку,
`returnFinded` ещё `false`, и исключение из `finally` заменяет исходное:

```petty
func f() : int32 { return true; }   # ожидается «Cannot convert from bool to int32»
```

выдаёт ` error on (2;1) : Function 'f' : not all code paths return a value` (с пустым типом ошибки).
Тест: `KnownBugTests.ErrorInsideNonVoidFunctionIsNotMasked`.

### 2.2. Внутренние исключения вместо ошибок компиляции

Конструкции, которые проходят парсер, но вызывают системное исключение вместо понятной ошибки.

| Пример | Исключение | Место |
|---|---|---|
| `var x : int32;` внутри функции | `NullReferenceException` | `CompileVarDef` компилирует `Value == null` |
| `var g : int32;` на верхнем уровне | `NullReferenceException` | `WriteGlobals` |
| `x += 1;` (и `-=`, `*=`, `/=`) | `NotImplementedException: +=` | `VisitVarAssignment` |
| `if 1 : { }` | `NotImplementedException` | `VisitIf` — нет сообщения об ошибке типа |
| `var g = f;` (функция как значение) | `Error: Value required` с позицией `(0;0)` | `GetInstanceSymbol` |
| `class A : { func A() { } }` + `A()` | `Error: Function 'A' is already exist` с позицией `(0;0)` | `BasicConstructorSymbol` |

Тест: `KnownBugTests.NoInternalExceptions`.

### 2.3. Сдвиг столбцов в позициях токенов

Идентификаторы на первой строке получают столбец на 1 больше настоящего, а символы (`=`, `;`, …) на
остальных строках — на 1 меньше. Номера строк верны.
Тест: `KnownBugTests.TokenColumnsAreConsistentAcrossLines`.

### 2.4. Командная строка

- При ошибке компиляции код выхода — **0**: обработчик в `Program.Main` печатает ошибку и делает `return`,
  не меняя кода выхода.
- Ошибка выводится через `Exception.ToString()`, то есть вместе со стеком вызовов компилятора.
- Отсутствующий входной файл даёт необработанное `FileNotFoundException`: `GetFileText` вызывается вне
  `try`.

## 3. Не реализовано

| Возможность | Состояние |
|---|---|
| `else` | ключевое слово есть, парсер — нет |
| Циклы | отсутствуют (только рекурсия) |
| Операторы сравнения кроме `int32 == int32` | нет `!=`, `<`, `>`, `<=`, `>=`; нет `==` для `float32`/`bool` |
| Логические операторы | нет `and`/`or`/`not` |
| Унарный минус | только как часть числового литерала; `x-1` без пробелов — синтаксическая ошибка (тест `KnownBugTests.SubtractionWithoutSpaces`) |
| Составное присваивание | разбирается, не анализируется |
| Строки | нет класса `String`; литерал даёт ошибку |
| Символьные литералы | `_addChar` не поглощает закрывающую `'` → `'a'` даёт `Char termination required`; парсер `Char` не обрабатывает |
| `import` / `package` | только ключевые слова |
| Наследование | ID родителя пишется в байткод, но члены не наследуются; подтипов нет |
| Пользовательские конструкторы | метод с именем класса конфликтует с базовым конструктором; аргументы конструктора не поддерживаются |
| Доступ к полям без `self.` | не поддерживается |
| Вложенные классы | молча игнорируются |
| Индексатор `a[i]` | поля `ArrayAppealArguments*` в AST есть, разбор — нет |
| Массивы других типов | `Array` хранит только `int32` (`get`/`set`) |
| `Object` как универсальный тип, приведения вверх/вниз | нет подтипов и проверок приведения в рантайме |
| Функции первого класса, замыкания | нет |
| Использование до объявления | функции и классы должны быть объявлены выше места использования (кроме методов внутри класса) |
| Проверка всех путей возврата | проверяется только наличие хотя бы одного `return` |
| Переполнение целых | не проверяется |

## 4. Качество кода

- **Дублирование кода:**
  - `Lexer`: пары `_addX` / `_processX`; вторые не используются.
  - `Analyzer`: `ResolveFuncDecl` и `VisitFuncDeclWithoutBlock` почти идентичны;
    `VisitVarDef` и `ResolveFieldsDecl` — тоже.
  - `Compiler`: две перегрузки `WriteFunctions` и `SortFunctionsByID`.
  - Два `ContainsOverload` в `FunctionSymbol`.
- **Мёртвый код:** `Parser.parseIdentifier(Expression)`, `parseAfterIdentifierExpression`,
  `IdentifierExpressionPart.SelfPushBytes`/`Last()`, `ScopeType.Package`, `Native.Inited`,
  `Compiler.GlobalsLenght`, неиспользуемые `using` в `Compiler.cs` (`System.Buffers`, `System.Numerics`,
  `System.Reflection`).
- **Опечатки в идентификаторах:** `returnFinded`, `GlobalsLenght`, `isMultyLine`, параметр
  `arrayAppealArgumentsAftersFuncCall`.

## 5. Связь с VM

Найдено при сверке с `~/PettyLang/Interpreter`:

- `ARRAY_CLASS_ID` в `ArrayTools.h` равен 7, а в компиляторе `Array` имеет ID 3 (7 — это `function`).
  Пока VM не проверяет класс массива, это незаметно, но расхождение стоит устранить до появления проверок
  типов в рантайме.
- Загрузчик функций и методов должен после чтения поля `length` сдвигаться ровно на `length` байт
  (см. [04-bytecode.md](04-bytecode.md#8-порядок-загрузки-в-vm)).

## 6. Рекомендуемый порядок исправлений

1. Адреса переходов во вложенных `if` (1.1), приведение к тому же типу (1.2, #7) и культура парсинга
   чисел (1.3) — небольшие правки, устраняют неверный байткод.
2. Подмена ошибок в не-`void`-функциях (2.1, #8) и код выхода при ошибке компиляции (2.4).
3. Сортировка функций (1.4) и замена `NotImplementedException`/`NullReferenceException` на понятные ошибки
   (2.2); инициализация переменных без значения значением по умолчанию.
4. Языковые возможности: `else`, циклы, операторы сравнения, `POP` для отбрасываемых значений.
